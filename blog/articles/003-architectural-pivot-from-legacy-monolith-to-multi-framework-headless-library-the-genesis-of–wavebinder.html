Architectural Pivot: From Legacy Monolith to Multi-Framework 'Headless' Library.
The Genesis of Wavebinder

February 04, 2026 by Senior Software Engineer / Lead Architect

Introduction: Risk Mitigation and Diversification Strategy

Several years into the legacy modernization project, the development team had expanded to 9 members, acquiring deep vertical expertise in managing complex interfaces. However, the company faced a significant Client Concentration Risk: operations depended almost exclusively on a single multinational client. Any interruption in this commercial relationship would have compromised business continuity.

Diversifying the client portfolio became a priority strategic requirement. The goal was to transform the acquired intellectual property into a marketable software asset. Analyses of previous "productization" attempts (a proprietary full-stack framework and a No-Code platform) highlighted the need for a new approach: abandoning the sale of a monolithic platform in favor of a modular, integratable solution.

Abstraction of Logic: Transition to a "Headless" Architecture

The genesis of Wavebinder is the result of an architectural rationalization process. A value analysis of our technology stack revealed that our competitive advantage did not lie in the persistence layer (Database) or the presentation layer (UI), but in the orchestration engine for dependencies and business rules.

We therefore opted for a sharp decoupling of the logic engine:

  • Removal of Persistence Constraint: Dependence on a rigid database schema was eliminated. Metadata and rule definitions were migrated to static configuration files (JSON/TypeScript), ensuring portability and versioning via Git.
  • Headless Approach: We removed any dependency on the visualization layer. The library imposes no layout or graphical components, limiting itself to managing the application state.

The technical objective was to provide a State Management Engine capable of centralizing validations and dependencies, leaving the developer with full autonomy over the User Interface implementation.

Non-Functional Requirement: "Framework Agnostic" Design

A fundamental requirement established during the design phase was cross-platform support. Given the fragmentation of the Frontend ecosystem, limiting compatibility solely to Angular (the original project's technology) would have drastically reduced the potential market.

To ensure interoperability with React, Vue.js, and Angular, we adopted the principles of Clean Architecture (or Hexagonal Architecture), structuring Wavebinder around a Core Layer (Pure TypeScript). This core is devoid of external framework dependencies and contains the configuration parsing logic, the dependency graph (DAG - Directed Acyclic Graph) for event resolution, and reactive state management.

This Separation of Concerns allows for maintaining a single code base for business logic while ensuring a native Developer Experience regardless of the stack used.

Operational Implementation: Declarative Graph Modeling and API Surface

Adopting Wavebinder shifts the development paradigm from imperative logic ("if A changes, then update B") to data-driven declarative modeling. The heart of the system lies in representing the application state as nodes in a directed graph.

Schema Definition and Dependency Injection

Instead of writing glue code to manage event cascades, the developer defines the data structure through a JSON configuration object. As illustrated in the technical documentation, each node in the graph (e.g., region, province, city) is described via key properties:

  • Metadata and Storage: The data type (type, e.g., "MULTI" for lists or complex objects) and the destination path in the data model.
  • Loading Actions (la): The declarative definition of how data is retrieved (e.g., a REST GET call, the associated service name, and the dynamic endpoint).
  • Dependency Array (dep): The explicit list of nodes upon which the current element depends. Wavebinder uses this information to automatically build the dependency network.

This configuration, easily manageable via a dedicated CLI tool to simplify initial scaffolding, allows for completely abstracting the complexity of many-to-many relationships between components.

Runtime and Graph Resolution

Integration into the project occurs via standard NPM (npm install wave-binder). The operational lifecycle follows three distinct phases:

  • Instantiation: The JSON configuration is passed to the WaveBinder class constructor, along with external services (extApis) and custom functions.
  • Building (Tangling): The wb.tangleNodes() method triggers graph analysis, resolving dependencies and preparing reactive listeners.
  • Interaction: Once the graph is "tangled," the library exposes a lean API surface for runtime interaction.

Interaction via API

The interface exposed to developers abstracts the underlying business logic. Methods like getNodeByName() or getNodeByNameAndType() allow for retrieving specific node instances. State updates occur through semantic methods such as setSelection() (to select a value in a list) or next() (to emit new values, leveraging its RxJS-based nature).

In this scenario, the frontend developer does not need to worry about when to call the API for cities if the province changes; they simply need to notify the province node that the selection has changed. Wavebinder, consulting the graph, will automatically invalidate dependent nodes and trigger the necessary Loading Actions.

Conclusion: Standardization and Scalability

The library does not impose architectural constraints on the entire application stack but positions itself as a targeted solution for automating complexity in business logic management.

Developers retain the freedom to select their preferred UI component libraries and frontend framework, delegating event propagation management to Wavebinder. This approach drastically reduces "boilerplate" code and minimizes the technical debt associated with maintaining complex conditional logic.
